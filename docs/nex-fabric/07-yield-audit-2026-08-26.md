# Yield Audit · 2026-08-26 · Chief Architect

Trace-one-candidate investigation of why NEX processes hundreds of records per cycle and saves zero.

## Method

- 7 combos observed across 3 verticals (food, market, transport) in the last 12h
- Aggregate: 1,129 candidates examined via cycle summary data + destination-table inspection
- Cross-checked: dedupe_hash matches, cross-cycle stddev, OSM source_updated_at freshness
- Zero code touched · zero speculation · direct DB SQL only

## Loss categorisation (Philip's required buckets)

| Loss category | % of 1,129 candidates | Root cause |
|---|---|---|
| Provider returned nothing | <1% | 1 sleman-north cycle · PROVIDER_ERROR outlier |
| Extraction lost | 0% | every returned candidate examined |
| Classification — exact hash | ~90% | dedupe_hash collision with existing row |
| Classification — fuzzy high | ~5% | name-similarity + coord-proximity above 0.85 |
| Classification — ambiguous | ~2% | fuzzy score 0.60-0.85 · held for admin review |
| Gate rejected | 0% | no new candidates ever reach gates |
| Persistence rejected | 0% | no new candidates ever reach persistence |

**100% of candidates die at Phase B (classification/dedup). Nothing reaches gates. Nothing reaches persistence.**

## Root cause

Dedup is CORRECT. Not over-aggressive. Every "matched_exact" corresponds to an existing row seeded on 2026-08-22/23/24 from the same OSM data.

Evidence:
- klaten-east bbox has exactly 25 rows in DB · matches the 25 exact-classifications every cycle
- stddev = 0 across 11 klaten-east cycles · providers return identical responses cycle-to-cycle
- `MAX(source_updated_at) = 2026-08-23T11:34Z` · OSM community edits stopped 3+ days ago for our covered geographies

**Yield=0 is the honest answer for the current provider mix × covered geography. NEX is not broken. Providers have given us what they have.**

## Philip's decision (2026-08-26)

**Pivot workforce to enrichment / freshness re-verification against the existing 8,818 rows.** Don't waste cycles re-discovering the same rows.

Reasoning: workforce infrastructure (scheduler, orchestrator, walker, persistence contract, watchdog) is proven. Redirecting the same machinery to a productive job (fill missing phones/websites/hours · re-verify existing entities are still active) maintains all invariants while producing real value.

## What NOT to build (rejected options)

- Provider Router — providers are healthy · problem is upstream data
- Taxonomy Brain — same providers · same coverage
- Multi-provider adapters — adding providers when loss isn't at provider stage is expensive misdirection
- Work-item reshape — no evidence current shape is the bottleneck
- MAX_SLOTS bump — 561/hour already processed
- Cost oracle walker integration — no paid providers wired
- Fabric Phases 4-7 from Track D — none address the actual bottleneck

## Options considered but deferred

1. Extend market walker Overpass query (`shop=*` + `marketplace=yes`) · marginal value
2. Walk new city geography (Balikpapan/Medan/Makassar/Manado) · may hit similar stagnation after initial seed
3. FSQ OS Places bulk ingest · 1-2 day project · genuinely uncorrelated source

Any of these could earn its existence LATER with fresh evidence. Not now.

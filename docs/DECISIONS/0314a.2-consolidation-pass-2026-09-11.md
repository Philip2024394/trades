### 3 · Founder decision · **CANDIDATE A** · Three orthogonal taxonomies · recorded 2026-09-11

> *"NEX maintains three orthogonal classification dimensions: LAM Object Type, Domain, and Category. LAM Object Type identifies the structural kind of NEX logical object; Domain identifies the subject-matter area the object concerns; Category identifies a governed classification within the relevant domain. No dimension may be silently substituted for another. Existing physical fields such as Supabase knowledge_records.category are physical representations of classification data and do not independently define NEX logical domain authority. Domain taxonomy, category taxonomy, and LAM Object Type taxonomy remain separately governed and versioned. A future hierarchical relationship between Domain and Category may only be introduced through an explicit founder-authorised ADR."*
>
> — Philip · 2026-09-11

**Doctrinal principles locked by this decision:**

> **NEX maintains three orthogonal classification dimensions:**
> 1. **LAM Object Type** · structural (Language · Semantic · People-Say · Domain Knowledge · Provenance · Governance · TE-verdict · Contradiction · Confidence · Version · Runtime · Competency · Authorisation · Bridge)
> 2. **Domain** · subject-matter (staircase · kitchen · door · flooring · programming · accommodation · food · etc. · authored in a future ADR)
> 3. **Category** · governed logical classification WITHIN the relevant domain
>
> **No dimension may be silently substituted for another.**
>
> **Category is a logical classification dimension.** Existing physical fields such as Supabase `knowledge_records.category` are physical representations of classification data · they do NOT independently define NEX logical domain authority. This is consistent with ADR-0310 Rule R4 (physical storage does not determine logical authority).
>
> **All three taxonomies are separately governed and versioned.**
>
> **No hierarchical relationship** between Domain and Category is introduced by this ADR. A future hierarchical model requires an explicit founder-authorised ADR.

### 4 · Canonical rule · R-DOMAIN-01.v1.0.0

**Three orthogonal classification dimensions:**

```
Every NEX logical object may be classified along up to three orthogonal axes:

     LAM Object Type       Domain               Category
     (structural)          (subject-matter)     (governed classification
                                                 within a domain)
         │                     │                     │
     14 canonical         Founder-authored     Founder-authored
     types (from          taxonomy             taxonomy per domain
     ADR-0309.1                                 (or shared if founder
     + Bridge from                              declares so in ADR)
     ADR-0312)
```

**Enforcement rules:**

- Every canonical row may carry up to three classification fields (LAM object type · domain · category) as appropriate to its object type
- Guardian rejects writes that use one dimension in place of another (e.g. putting a domain value in a category field)
- The three taxonomies are versioned independently:
  - LAM object type version (from ADR-0309.1 · currently v1)
  - Domain taxonomy version (to be authored in ADR-0314a.2.s · e.g. `domain_taxonomy.v1.0.0`)
  - Category taxonomy version (per domain · to be authored per companion ADR or in ADR-0314a.2.s.cat)
- Physical fields on any substrate that carry classification data are physical representations of these logical dimensions · they do not define the logical dimensions themselves
- Substrate reconciliation: `Supabase.knowledge_records.category` values ("NEX door" · "NEX kitchen" · etc.) map to the logical Category dimension via a mapping declared in a companion ADR · they are NOT the definition of Category

**Anti-substitution guardrail:**

### R-10 test · is R-10 a layer or a promotion gate?

**Founder's hypothesis:** R-10 may be better understood as a promotion gate that receives the outputs of the other rules, rather than Layer 7 in a linear stack.

**Analysis:**

Reading R-10.v1.0.0's canonical rule verbatim:
> *"Verifier verdicts terminate at `truth_engine_ok` unless the target LAM object type's authorisation policy explicitly permits autonomous promotion to `AUTHORITATIVE`."*

R-10 does NOT itself produce a verdict on a claim. R-10 operates on the AGGREGATE state after other Truth Engine rules have run. It consumes:

- The aggregate `truth_engine_ok` state (the union of individual rule verdicts having passed)
- The per-LAM-object-type authorisation policy (per companion ADR-0314a.2.a-h)
- The `authorised_by` field / `knowledge_feedback` presence (founder overrides)
- Confidence floor per policy (from R-11 · normalised at Router boundary)
- Provenance / governance state per policy

R-10 then decides one thing: **does this object promote from `truth_engine_ok` to `AUTHORITATIVE`, or stay at `truth_engine_ok`?**

By contrast, R-01 · R-02 · R-03 · R-05 · R-07 · R-12 · R-13 · R-20 all produce verdicts on specific properties of a claim:
- R-01 · does the numeric claim satisfy the domain threshold?
- R-02 · does the audience match the category policy?
- R-05 · is the cited authority in the registry?
- R-07 · is the connection plausible under the deterministic rules?
- R-13 · does the relation_kind resolve to the canonical vocabulary?
- R-20 · is there a deterministic contradiction?

**These are EVALUATION rules · not gate rules.**

Similarly, R-11 · R-17 · R-18 are not evaluation rules in the same sense:
- R-11 (confidence) is a **normalisation** rule at Router boundary · not a verdict on claim truth
- R-17 (versioning) is a **side-effect** rule fired by significant change events · not a verdict
- R-18 (verifier identity + rule_set_version) is a **meta** rule about how verdicts are RECORDED · not a verdict

**Conclusion: the founder is correct.** R-10 is architecturally a **promotion gate**, not a peer layer to R-01/R-02/R-20. The first-pass 9-layer linear stack was oversimplified.

# 0309.1 · NEX Logical Authority Model (LAM)

**Status:** Proposed · doctrine only · database freeze in force
**Founder:** Phillip · directive 2026-09-11
**Amends:** ADR-0309 (Layered Architecture · Rule 15 already added)
**Depends on:** `data/nex-english-source-map/reconciliation-2026-09-11.md` · `data/nex-english-source-map/gate-2-supabase-audit.md`

---

## Purpose

The reconciliation audit and Gate 2 Supabase audit revealed that NEX already contains substantial knowledge across three physical substrates — `nex_dev` Postgres, NEX-dedicated Supabase, repository files. Each substrate has independent governance, provenance, and Truth Engine primitives running in different states of maturity.

This ADR does NOT decide where anything moves. It answers a deeper question:

> **"What is NEX's logical authority model when knowledge already exists across multiple physical substrates?"**

The LAM is doctrine. It governs every future ADR that touches knowledge — including ADR-0310 when that eventually drafts.

## Founding Doctrine (Rule 15 of ADR-0309 restated + expanded)

> **Physical storage location does not determine logical knowledge authority. NEX maintains one logical authority per knowledge object and per knowledge layer, even if implementation currently spans multiple physical stores.**

Consequences:

1. Any read path resolving a knowledge object must be **explicit** about which physical store(s) it consults AND which is the logical authority.
2. Any write path promoting a knowledge object must pass through the logical-authority pipeline (Guardian → Truth Engine) **regardless** of physical store.
3. Two physical rows describing the same logical object may coexist temporarily. Exactly one is authoritative. The others are copies, caches, or superseded.
4. **The physical topology is an implementation detail. The logical authority is the doctrine.**

## The 13 logical object types

Every piece of English/knowledge/language content in NEX belongs to exactly one of these types.

| # | Logical Object | Scope · one-line definition |
|---|---|---|
| 1 | **Language object** | Word-level linguistic knowledge (POS · CEFR · pronunciation · bilingual definitions · examples · register · variety · frequency) |
| 2 | **Semantic object** | Concept + distinct senses + disambiguation contexts + concept-to-concept relationships |
| 3 | **People-Say object** | Folk-phrase → canonical concept mapping (founder-authored · Rule B no-AI · Rule C attributable) |
| 4 | **Domain Knowledge record** | Structured document about a domain (business/staircase/kitchen/accommodation/etc) with status ladder |
| 5 | **Provenance record** | The `source_ref` + trust layer for any other object · answers "where did this claim originate?" |
| 6 | **Governance record** | Founder judgment (`knowledge_feedback` · authored_by/authorised_by/reviewed_by fields on records) |
| 7 | **Truth Engine verdict** | Guardian/Truth-Engine decisions promoting/blocking/deprecating an object |
| 8 | **Contradiction record** | A detected conflict between two claims · with resolution status |
| 9 | **Confidence score** | Numeric trust attached to an object at a point in time |
| 10 | **Version record** | Historical snapshot of an object at a specific version |
| 11 | **Runtime/retrieval/cache datum** | Materialised for query speed · never authoritative · rebuildable from canonical (question_variant · semantic_question_index · hot tier caches) |
| 12 | **Competency/training record** | What NEX1 has demonstrated it can do (`nex_agent.*`) · NEVER mixed with knowledge |
| 13 | **Authorisation/action policy** | Founder-approved actions NEX may take (auto-apply gates · pre-cleared categories · doctrine rules) |

## Object Attribute Matrix

For each of the 13 logical object types · 16 attributes. This is the doctrine grid.

Key legend:
- **LO** = Logical Owner (who is responsible)
- **CA** = Canonical Authority substrate (where truth lives today)
- **PS** = Physical Substrate(s) that hold rows of this type
- **Cp** = Copies permitted? (Y/N + rule)
- **Dv** = Derivatives permitted? (Y/N + rule)
- **Pv** = Provenance required for authoritative status?
- **Gv** = Governance (founder approval) required for authoritative status?
- **Cn** = Contradiction handling
- **Cf** = Confidence handling
- **Ver** = Version handling
- **Pr** = Promotion rule (draft → authoritative)
- **Rt** = Retrieval rule
- **Sy** = Sync rule between physical substrates
- **Cr** = Conflict-resolution rule when substrates disagree
- **Au** = May become authoritative?
- **Sp** = Supporting-only classification?

## Cross-layer rules

### Promotion (draft → authoritative)

Every object type has its own promotion ladder. The LAM does NOT require a single unified ladder. It DOES require:

1. Every promotion cites the substrate that made the decision.
2. Every promotion emits an audit event.
3. Founder authorisation is required for:
   - Language: `flagged_for_review=false` transition (currently implicit via `corpus_layer1`)
   - Semantic: any concept/sense marked `authoritative` (per ADR-0308)
   - People-Say: every entry (Rule B)
   - Domain Knowledge: `AUTHORITATIVE` status on `knowledge_records`
   - Authorisation: every ADR

### Retrieval

1. Chat and NEX1 MUST read the same logical authority for the same layer.
2. If a runtime cache exists, it must be rebuildable from canonical.
3. Cross-substrate retrieval requires an explicit adapter (none built yet).

### Sync

1. Canonical rows are NOT auto-synced between substrates. Sync is either NONE or one-direction publish-with-provenance.
2. Any sync design must preserve: `authored_by` · `authorised_by` · `verified_at` · `source_ref` · `record_version` · governance linkage.

### Conflict resolution (two substrates disagreeing)

Ordered rules:

1. Higher-status wins (`AUTHORITATIVE` > `truth_engine_ok` > `guardian_ok` > `draft`).
2. If both `AUTHORITATIVE`, later `authorised_at` wins.
3. If tied, founder resolves.
4. Never silent — every conflict resolution emits a governance row.

## The 11 failure modes the LAM prevents

The LAM MUST prevent every one of these. Any future ADR that risks any of them requires explicit founder waiver.

1. **Duplicate canonical brains** — two physical substrates each claiming to be authoritative for the same logical object.
2. **Silent authority conflicts** — Chat reads Supabase while NEX1 reads Postgres for the same concept.
3. **Copying supporting data and accidentally promoting it to canonical** — runtime cache flipped to authoritative without going through promotion.
4. **Migration before row-level reconciliation** — moving `knowledge_records` into `nex.*` without knowing whether `nex.business_knowledge` (1258) already contains overlapping rows.
5. **Founder governance being lost during migration** — moving a record without bringing its `knowledge_feedback` and `authorised_by`.
6. **Contradiction history being discarded** — the 8 real `contradictions` in Supabase must survive any consolidation.
7. **Provenance being detached** — a record moving without its `sources` row.
8. **Confidence/version information being lost** — moving a record without bringing `confidence_scores` history and `record_versions`.
9. **English semantic knowledge being mixed with domain knowledge** — putting `concept:migration.database_schema_change` into `knowledge_records` or vice versa.
10. **Knowledge being mixed with agent competency** — putting a `nex_agent.*` row into a knowledge table.
11. **Runtime retrieval data being mistaken for canonical knowledge** — treating `nex.question_variant` (25456) as a canonical question corpus.

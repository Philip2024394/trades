## Section 3 · Production-state model · locked

A Claim (per ADR-0314g §3 · nine distinct object types) in the constitutional pipeline may occupy exactly one of the following states:

| # | State | Meaning | Reached from |
|---:|---|---|---|
| 1 | `ACQUIRED` | Raw Capture + Candidate exist · not yet inspected by Lab-Guardian | Acquisition Fabric Layer B |
| 2 | `LAB_CANDIDATE_REJECTED` | Lab-Guardian rejected · reason recorded with `lab.` prefix · dropped from pipeline | `ACQUIRED` |
| 3 | `LAB_CANDIDATE_ACCEPTED` | Lab-Guardian accepted · Claim ready for Truth Engine input | `ACQUIRED` |
| 4 | `VERIFIER_VERDICT_ISSUED` | Truth Engine produced a `VerdictEnvelope` · not yet inspected by TE-Guardian | `LAB_CANDIDATE_ACCEPTED` |
| 5 | `TE_GUARDIAN_REJECTED` | TE-Guardian rejected the envelope · reason recorded with `te.` prefix · Claim discarded | `VERIFIER_VERDICT_ISSUED` |
| 6 | `TE_GUARDIAN_ACCEPTED` | TE-Guardian accepted the envelope · Claim is constitutionally sound | `VERIFIER_VERDICT_ISSUED` |
| 7 | **`AWAITING_R10`** | Claim is constitutionally verified · but R-10 authorisation is not available (Stage 2 territory) · **Claim is NOT AUTHORITATIVE** · Claim does NOT enter specialist substrate via the constitutional pipeline | `TE_GUARDIAN_ACCEPTED` |
| 8 | `AUTHORITATIVE` | R-10 authorised · Claim written to NEX Storage as canonical Knowledge (Stage 2 only · **not reachable at Stage 1b**) | `AWAITING_R10` (Stage 2 only) |
| 9 | `CONTRADICTED` | R-20 detected a deterministic contradiction · flagged for Contradiction Handler | any post-verification state |
| 10 | `WITHDRAWN` | Source withdrew · founder-declared · or admin action · Claim retired · Evidence preserved | any state |

**The Stage 1b production-state model reaches `AWAITING_R10` as its constitutional terminus.** It does not reach `AUTHORITATIVE`. That transition requires Stage 2 R-10.

### 3.1 · Explicit R-10-absent safety boundary (locked)

**Founder verbatim:** *"R-10 not yet available · therefore NOT AUTHORITATIVE."*

At Stage 1b commencement:

- ❌ **No Claim reaches `AUTHORITATIVE` via the constitutional pipeline.** The transition `AWAITING_R10 → AUTHORITATIVE` requires Stage 2 R-10 policies · which do not exist yet.
- ✅ Claims reach `AWAITING_R10` and remain there indefinitely (until Stage 2 lands).
- ✅ The Truth Engine + TE-Guardian are exercised at production scale · verdicts persisted · Guardian decisions persisted · but no Claim is promoted.

**This is the honest safety boundary.** Stage 1b proves the pipeline works at production scale without granting it authoritative-writes authority.

### 3.2 · Coexistence with legacy AUTHORITATIVE writes

Today's ~40,000 AUTHORITATIVE rows in `nex.accommodation_business` · `nex.food_business` · `nex.service_business` · `nex.brain_attractions` · etc. were produced BEFORE the constitutional pipeline existed. They arrived via the legacy Lab-verified → executor → specialist-table path (per ADR-0314a.2.s Lab Audit §6).

Stage 1b MUST NOT retroactively invalidate them · and MUST NOT silently make them constitutionally verified either. Three founder-decision options for coexistence (this ADR does NOT choose · founder chooses at "AUTHORISE STAGE 1b"):

| Option | Description | Effect |
|---|---|---|
| **C-α · Legacy path continues in parallel** | Existing executor pipeline continues producing new legacy-AUTHORITATIVE rows via the pre-constitutional path. Stage 1b constitutional pipeline runs alongside in shadow. New rows arrive both ways. | Operations continue · shadow verdicts record what the constitutional pipeline WOULD have decided · reconciliation deferred to Stage 2 |
| **C-β · Legacy path freezes** | Existing executor pipeline paused. All new rows must flow through the constitutional pipeline · terminating at `AWAITING_R10` · never reaching AUTHORITATIVE. | Hardest safety boundary · but halts new AUTHORITATIVE writes until Stage 2 |
| **C-γ · Legacy path continues · but rows are marked** | Existing executor still promotes to AUTHORITATIVE · but rows are tagged `legacy_pre_constitutional=true`. Stage 2 R-10 policies will retroactively adjudicate legacy rows. | Middle ground · operations continue · legacy rows explicitly marked for future R-10 review |

**Recommendation for founder consideration** (NOT a locked choice): **C-γ**. Preserves operational continuity · marks legacy rows explicitly · defers reconciliation to Stage 2 R-10 policies where founder can author per-Domain/per-LAM policies for retroactive adjudication.

Whichever option founder chooses at "AUTHORISE STAGE 1b" · this ADR locks the invariant: **no NEW row moves from `AWAITING_R10` to `AUTHORITATIVE` via the constitutional pipeline until Stage 2.**

### 3.3 · State transitions (locked)

Legal transitions:

```
        ┌──────────┐
        │ ACQUIRED │
        └────┬─────┘
             │ (Lab-Guardian inspects)
   ┌─────────┴──────────┐
   │                    │
LAB_CANDIDATE_REJECTED  LAB_CANDIDATE_ACCEPTED
   │                    │
   ▼                    │ (Truth Engine runs)
[dropped]                ▼
                    VERIFIER_VERDICT_ISSUED
                         │ (TE-Guardian inspects)
                ┌────────┴────────┐
                │                 │
        TE_GUARDIAN_REJECTED  TE_GUARDIAN_ACCEPTED
                │                 │
                ▼                 │ (R-10 not available at Stage 1b)
             [discarded]           ▼
                              AWAITING_R10
                                   │
                                   │ (Stage 2 R-10 · not authorised at Stage 1b)
                                   ▼
                            [AUTHORITATIVE · Stage 2 only]

Any state → CONTRADICTED (R-20 fires deterministic contradiction)
Any state → WITHDRAWN (source withdrawal · founder action · admin)
```

Guardian invariant: **no state may be skipped**. A Claim cannot go `ACQUIRED → TE_GUARDIAN_ACCEPTED` directly. Lab-Guardian must inspect. Truth Engine must run. TE-Guardian must inspect. Each transition is recorded with reason + evidence.

## Section 4 · Required substrate additions (list only · DDL deferred to Stage 1b implementation)

Stage 1b activation would require the following substrate additions. This ADR ENUMERATES · does not create.

### 4.1 · Production TE-Guardian ledger (distinct from legacy Lab-Guardian ledger)

| Table | Purpose | Distinct from |
|---|---|---|
| `nex.te_guardian_kept_event` | TE-Guardian ACCEPT decisions in production | `nex.gate_kept_event` (Lab-Guardian's ledger · preserved per ADR-0314f) |

### 4.2 · Production verifier verdict + reproducibility substrate (analogs of Stage 1a nex_test.*)

|---|---|---|

| `nex.reproducibility_run` | Production determinism proof runs (if founder requires · e.g. weekly proof) | `nex_test.reproducibility_run` |

Constraint: `authorisation_policy_ref` column present · **must be null at Stage 1b** (per §3.1 R-10-absent boundary). CHECK constraint enforces null-only at Stage 1b · relaxed to nullable when Stage 2 lands.

### 4.3 · Claim verification state table

| Table | Purpose |
|---|---|
| `nex.claim_verification_state` | Tracks the current state of each Claim (`ACQUIRED` / `LAB_CANDIDATE_REJECTED` / `LAB_CANDIDATE_ACCEPTED` / `VERIFIER_VERDICT_ISSUED` / `TE_GUARDIAN_REJECTED` / `TE_GUARDIAN_ACCEPTED` / `AWAITING_R10` / `AUTHORITATIVE` / `CONTRADICTED` / `WITHDRAWN`) · references Claim by (subject_entity_id · attribute · claim_id) · records state timestamps + evidence pointer |

References specialist tables by (schema · table · row_id) rather than adding state columns to specialist tables. Preserves specialist tables untouched.

### 4.4 · Claim + Evidence tables (new · per ADR-0314g §3 object model)

| Table | Purpose |
|---|---|
| `nex.claim` | Per-Claim row: subject Entity ID · attribute · value · unit · Evidence pointer · verification_state pointer · claim_id · created_at · created_by |
| `nex.evidence` | Per-Evidence row: claim_id · source_id · raw_capture_id · extraction_method · extraction_confidence · timestamp · immutable |

### 4.5 · Legacy-row tagging (only if coexistence option C-γ chosen)

If founder chooses coexistence option C-γ · specialist tables gain a `legacy_pre_constitutional` boolean column (nullable · default false for new rows · true for existing rows at migration time). If C-α or C-β chosen · no legacy-row tagging.

## Section 6 · Coexistence rollout stages (Shadow → Rejection-Active)

Whatever coexistence option founder chooses (C-α · C-β · C-γ · §3.2) · the rollout MUST proceed through two mandatory stages:

### 6.1 · Shadow mode (Stage 1b.5)

**Behaviour:**
- Production adapter runs on new Claims arriving from acquisition
- Truth Engine produces `VerdictEnvelope` per Claim
- TE-Guardian inspects · records decision
- Verdict + Guardian decision persist to new tables
- **BUT no state change affects any downstream promotion**
- Legacy executor pipeline behaves as it does today (unchanged)
- New Claims accumulate in `nex.claim_verification_state` with state `TE_GUARDIAN_ACCEPTED` or `TE_GUARDIAN_REJECTED` · never reaching `AWAITING_R10` in a blocking sense

**Purpose:** observe · measure · verify that Truth Engine + TE-Guardian produce sensible verdicts at production scale before allowing them to gate anything.

**Metrics to review before advancing to 1b.6:**
- TE-Guardian accept rate (per Domain · per Category · per source)
- TE-Guardian reject rate by canonical `te.` code (surface systemic issues)
- Pending-policy UNKNOWN rate (R-03 · R-05 · R-07 · R-12 · R-20 return UNKNOWN because policies pending)
- Contradiction detection rate (R-20 · but pending policy so mostly UNKNOWN)
- Determinism · byte-identical across sample replays

### 6.2 · Rejection-active mode (Stage 1b.6)

**Behaviour:**
- Production adapter still runs on new Claims
- Truth Engine + TE-Guardian continue producing verdicts + decisions
- **State transitions become authoritative for the constitutional pipeline:** rejected Claims do not proceed past their rejection state
- Claims that pass TE-Guardian reach `AWAITING_R10` and STOP (per §3.1 R-10-absent boundary)
- Legacy executor pipeline behaviour: per founder-chosen coexistence option (§3.2)

**Purpose:** activate the constitutional pipeline at production scale · with the honest R-10-absent boundary preserved.

### 6.3 · Founder gate between 1b.5 and 1b.6

Founder MUST explicitly authorise the transition from shadow to rejection-active. Master AI does NOT auto-advance based on metric thresholds. **This is a founder-authored constitutional decision · not an observation-driven autonomous progression** (per `feedback_observation_is_not_constitutional_authority.md`).

# ADR-0024: Every image asset carries its generation prompt / capture context

Status: Accepted
Date: 2026-07-27

## Context

Building the NEX directory revealed a compounding workflow gap. Philip has been generating staircase illustration imagery via ChatGPT and uploading it to `ik.imagekit.io/5vv5pw26q/`. Each upload lands with a filename like `ChatGPT Image Jul 25, 2026, 12_15_57 PM.png` — the original generation prompt (which fully describes the image content) is lost at save time.

When we then need to match those images to use cases (a directory card for a business specialising in glass balustrades needs a glass balustrade image, not a random oak stair) we discover we have **82 images with no record of what any of them depicts**. The only remaining signal is the surrounding context of wherever the URL happens to be referenced — insufficient for automated matching and impossible to grade for A+ quality without visual inspection.

The root cause is a missing manifest at creation time. The image itself doesn't carry provenance in metadata (PNGs generated by ChatGPT strip prompt info), and the human workflow "generate → upload → paste URL somewhere" has no mandated step for "and record what this is."

This isn't unique to the staircase batch. As NEX ships more AI-generated marketing imagery, logos, hero art, brain illustrations, banners, avatars, etc., the same gap will produce the same problem at larger scale.

## Decision

**Every image asset added to NEX must be recorded in a canonical image manifest at creation time.** No image URL is considered "in the system" until its manifest row exists.

### Manifest location

`data/nex-image-manifest.json` — git-versioned, single source of truth. Structure:

```json
{
  "version": 1,
  "images": {
    "<canonical_url>": {
      "source": "ai_generated" | "uploaded" | "screenshot" | "render_3d" | "photo",
      "original_prompt": "<full generation prompt if AI, else null>",
      "description": "<one-line human description of subject>",
      "tags": ["oak", "floating", "modern"],
      "a_plus": true,
      "subject_domain": "staircase" | "logo" | "avatar" | "wood-sample" | "hero-banner" | ...,
      "created_at": "<ISO timestamp>",
      "created_by": "<person or system>",
      "notes": "<optional freeform>"
    }
  }
}
```

### Required fields on every row

`url` (implicit — it's the key) · `source` · `description` · `tags[]` · `subject_domain` · `created_at`.
`original_prompt` is required when `source: "ai_generated"`.
`a_plus` defaults to false — flip true only after visual review.

### Enforcement

- **Any script or workflow that uploads to ImageKit / Supabase Storage / `public/` must append a manifest row as its final step.** No exceptions.
- **Any component or code that references a hero image URL should look it up from the manifest by tag intersection**, not hardcode the URL. Hardcoding is allowed only for one-off page hero art (documented per-file) where the manifest lookup adds no value.
- **CI grep check** (future): any URL under `ik.imagekit.io/5vv5pw26q/` or the nex-image Supabase buckets that appears in code but is not in the manifest is a violation to flag in review.

### Retroactive backfill for pre-rule images

The 82 existing untagged images are grandfathered via a one-time admin tool:

- Route: `/admin/image-tagger`
- Function: displays each pre-rule image at full size with tag inputs
- Output: writes rows into `data/nex-image-manifest.json`
- Owner: Philip runs it once; ~10-15 min for 82 images

New images generated after this ADR MUST NOT need the tagger — they should be tagged at creation.

## Consequences

**Positive:**
- Directory card auto-assignment, brain answer illustration, banner generation, hero art selection, and any future image-consuming feature can all read one manifest and pick the best match by tag intersection.
- Provenance is captured for every image — enforces ADR-0022 (no third-party image copy) by construction: any row with an unknown `source` or origin URL flags immediately.
- Design decisions become auditable: "why is this image on this card?" answered by the manifest row.
- No more archaeological "what's in this image?" work — the prompt IS the description.
- The manifest becomes a searchable image library index for internal use.

**Negative:**
- Adds a ~30-second manual step to every image generation. Real friction; unavoidable if the goal is durable metadata.
- The manifest file will grow; at scale a proper images table in Supabase may replace the JSON. Migration path is straightforward when needed.
- Some legacy scripts and workflows need updating to write manifest rows.

**Neutral:**
- The admin tagger is a one-time tool. Once the 82 backfill is done, it should quietly disappear from live routes (or gate behind an internal flag).

## Alternatives considered

- **EXIF / XMP metadata in the image file itself** — rejected. PNGs (which ChatGPT outputs) don't handle XMP as well as JPEG, and Supabase Storage / ImageKit CDNs strip metadata on transformation. Not durable.
- **Filename convention only** (`oak-floating-modern-01.png`) — rejected as sole solution. Filenames get truncated, mangled, and don't scale to compound descriptions. But a good filename remains a nice-to-have and complements the manifest.
- **Store prompts in a separate side-channel** (README, docs) — rejected. Drifts from the images. The URL is the natural key; a URL-keyed manifest is the only shape that stays honest.
- **Skip the retroactive backfill of the 82 pre-rule images** — rejected. The backfill unblocks directory card curation immediately, and the tool is small enough to justify building.
- **Automatic vision-model captioning of untagged images** — deferred. Interesting future capability; captions can be seeded from a vision model as a first pass, but Philip's human curation stays the final authority on A+ / subject tags.

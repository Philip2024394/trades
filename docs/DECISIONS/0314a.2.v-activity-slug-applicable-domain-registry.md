## Section 1 · Purpose

This ADR specifies the SHAPE and GOVERNANCE of the Activity Slug Applicable-Domain Registry required by §7.4.C1. The registry maps each of the 87 activity slugs (from `src/lib/nex/intelligence-storage-grid/accommodation/activity-taxonomy.ts` · 11 groups · 87 slugs) to a founder-authorised `applicable_domains: string[]` list — identifying the NEX Domain(s) in which each activity slug may legitimately be used.

**This ADR does NOT populate the registry.** Per §7.4.C1: *"Do not yet populate the registry unless separately authorised."* Per-slug `applicable_domains[]` values remain founder-authored per slug in a future ADR (candidate slot ADR-0314a.2.v.pop OR similar).

**This ADR IS:** the specification of the registry contract · the governance rules · the enforcement policy · the fail-closed default · the anti-substitution guardrail.

## Section 2 · Registry entry shape

Each registry entry conforms to the following shape (specification only · not implemented at substrate level yet):

```
ActivitySlugApplicableDomainEntry {
  activity_slug: string           // one of the 87 canonical slugs (verified against activity-taxonomy.ts)
  activity_group: ActivityGroup   // one of the 11 groups (NATURE · OUTDOOR · CULTURE · ENTERTAINMENT
                                  //   · WELLNESS · FOOD_EXPERIENCE · SHOPPING · NIGHTLIFE
                                  //   · TRANSPORT_HUB · SERVICE · OTHER)
  applicable_domains: string[]    // 0..N canonical Domain slugs from the Domain axis
                                  //   (accommodation · food · transport · business · travel · attractions · etc.)
                                  //   founder-authorised per slug · no AI inference
  authorised_by: string           // founder identity · always "Philip" for the initial locked entries
  authorised_at: ISO8601 string   // date of founder authorisation per entry
  authorisation_reason: string    // free-text · records the architectural reason the slug maps to those Domains
  status: "unknown" | "governed"  // "unknown" = fail-closed default · "governed" = founder-authored
  supersedes: string | null       // prior entry's id if this is a correction · null if first-time
}
```

**Cardinality:**
- One entry per slug per version (append-only · corrections require new entry with `supersedes`)
- Registry version tag: `activity_applicable_domains_registry.vN.N.N` (independent versioning per R-DOMAIN-01 discipline)

**Physical substrate:** to be authored in a future ADR-0314a.2.v.impl · candidate table `nex.activity_slug_applicable_domain` OR similar · NOT authored by this ADR.

## Section 3 · Governance rules

### 3.1 · Founder-authored only

Every `applicable_domains[]` value per slug is authored by the Founder in an explicit ADR entry. No AI inference · no similarity-based inference · no keyword-overlap inference · no cross-slug pattern inference. This is a hard prohibition per §7.4.C1.

### 3.2 · Domain-axis authority

Every value in `applicable_domains[]` must resolve to a canonical Domain slug from the Domain axis (per R-DOMAIN-01 · currently unlocked pending future companion ADRs · founder authors Domain slugs in ADR-0314a.2.s companions or their equivalents). References to non-Domain-axis values (e.g. an Operational Scope value or an Agent/Runtime Identity value) are G-2 non-bypass violations.

### 3.3 · Anti-substitution guardrail (per R-DOMAIN-01)

The `applicable_domains[]` field is a **classification/relationship mechanism** — it tells the Router *where* an activity slug is legitimately applicable · but it does NOT ITSELF classify an object's Domain. Specifically:

- A stored record's `domain` field carries a **single Domain value** (Domain axis)
- A stored record's `activity_slug` field (if any) carries a **single activity slug** (Category axis · shared cross-Domain)
- Guardian consults `applicable_domains[]` to check: *"is this record's Domain in the activity slug's applicable_domains list?"* — if yes, permit; if no, reject
- `applicable_domains[]` NEVER substitutes for the record's Domain field
- Using `applicable_domains[]` as a Domain field is a G-2 non-bypass violation (per R-DOMAIN-01 anti-substitution)

### 3.4 · Fail-closed default (per §7.4.C1 rule 5)

If an activity slug has no entry in the registry OR has `status: "unknown"`, then:

- Guardian REJECTS any write of a record with that slug into a Domain-typed field
- Router returns `unknown_applicable_domain` when asked "does this slug apply to Domain X"
- No inference · no partial-match · no group-level fallback (e.g. WELLNESS group is not automatically treated as applicable to Business Domain just because SHOPPING slugs are · founder decides per slug)

Rationale: per §7.4.C1, missing or ambiguous Domain applicability is **unknown/fail-closed until governed**. NEX doctrine "unknown is a verified fact, not a fabrication" (from ADR-0314 TE1) applies here.

### 3.5 · Multi-Domain applicability permitted

A slug MAY carry more than one Domain in `applicable_domains[]`. Examples given by founder 2026-09-11 (illustrative · NOT populated by this ADR):

- `scuba_diving` (candidate) → `[Attractions, Activities, Tourism]` (if Activities/Tourism ever become Domains)
- `airport_transfer` (candidate) → `[Transport, Accommodation]`
- `spa_massage` (candidate) → `[Business/Services, Wellness/Healthcare]` (if those Domains are ever established)

These are hypothetical shapes. No values authored by this ADR.

### 3.6 · Anti-Domain-inflation discipline (per founder feedback 2026-09-11)

The registry MUST NOT be used as evidence FOR creating new Domains. Specifically:

- Presence of orphan slugs (e.g. OUTDOOR verbs) whose `applicable_domains[]` is empty is NOT justification to invent an "Activities Domain"
- Orphan-slug promotion to a distinct Domain requires:
  1. Independent architectural evidence (specialist substrate · adapter · worker · classifier target · demand signal)
  2. A separate founder-authorised ADR with its own architectural inspection matrix (per the §7.2/§7.3/§7.4 pattern)
- Master AI MUST NOT infer that "we need a new Domain" from the shape of the taxonomy

Rationale: this is exactly the architectural creep §7.3 introduced discipline against. The Founder feedback 2026-09-11 verbatim: *"Don't let Master AI interpret the ~17 OUTDOOR verbs and say: 'Therefore we need an Activities Domain.' Not yet. That's exactly the sort of architectural creep we're trying to prevent."*

### 3.7 · Reversibility

- A slug's `applicable_domains[]` may be corrected in a future founder-authorised entry (append-only · `supersedes` field)
- A slug may be **promoted** to Domain status in a future founder-authorised ADR (creating a new Domain slug on the Domain axis) — in which case the `applicable_domains[]` of adjacent slugs may need updating (also founder-authored)
- A slug may be **demoted** or deprecated · in a founder-authorised entry with `status: "deprecated"` (this ADR does not currently define a deprecated status but reserves the naming)

## Section 4 · Founder-decision escalation for population

The registry is populated only through founder-authored decisions. Master AI CANNOT populate any entries autonomously.

Expected population workflow (specified here · not executed):

1. Founder authorises the population ADR (candidate slot **ADR-0314a.2.v.pop · Activity Slug Applicable-Domain Registry — Initial Population v1.0.0**).
2. That ADR presents evidence per slug (up to 87 evidence blocks) proposing `applicable_domains[]` per slug.
3. Founder locks each entry OR amends OR defers.
4. Locked entries carry the 8-field footer per R-DOMAIN-01 v1.0.0 pattern (Decision · Decided by · Decision date · ADR · Effective from · Supersedes · Reason).

**Expected sizing:** 87 slugs × ~7 fields per entry = ~600 authoring units. Founder should decide whether to author in one massive ADR or in group-scoped batches (per activity_group).

Master AI produces the evidence-presentation per slug when authorised. Founder locks or amends.

## Section 5 · Cross-references with other axes

Per §7.3-B1 five-axis architecture:

- **LAM Object Type** — activity taxonomy entries are Domain-Knowledge-shaped LAM objects (they carry claim-like structure with subject-matter content)
- **Domain axis** — `applicable_domains[]` references Domain axis values only
- **Category axis** — the activity taxonomy IS a Category-tier taxonomy per §7.4.C1 (shared cross-Domain)
- **Operational Scope axis** — activity slug harvest goes through `nex_lab_activities` (Operational Scope · Lab room) · unrelated to the applicable_domains[] classification
- **Agent/Runtime Identity axis** — activities Lab is served by `lab_harvest_activities` agent (Agent/Runtime Identity per §7.3) · unrelated

Guardian verifies at write time that:
- Domain field carries a canonical Domain slug (not a Category slug · not an activity slug)
- activity_slug field (if present) carries an activity slug from the canonical 87
- record's Domain is in the activity slug's `applicable_domains[]` per this registry

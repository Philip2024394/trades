# ADR-0018: Digital Twin Event Log · Append-Only Event Sourcing · Merchant-Homeowner Perspective Only at V0

Status: Draft (awaiting signoff)
Date: 2026-07-23
Related: `docs/PHASE_29_DIGITAL_TWIN_BLUEPRINT.md` · `docs/ES-01_ENGINEERING_EXECUTION_BIBLE.md` §14.1 (correction #6) · `docs/ES-02_DATA_AND_EVENT_ARCHITECTURE_V1.md` §5.1

## Context

Phase 29 Digital Twin creates a persistent replica of every real project, event-sourced so any prior state is reconstructable and no state change is silently overwritten. The event log is the substrate underneath every merchant-facing Twin surface.

Two decisions must be locked before any code:

1. **Event log schema.** Every future Twin behaviour derives from this schema. Getting it wrong later is not a rollback — it's a migration of every historical event ever written.

2. **V0 scope simplifications.** ES-01 §14.1 corrections #5 and #6:
   - Ship Twin V0 without BIM ingest (defer to V1)
   - Ship 2 perspectives (Merchant · Homeowner) not full Brain-perspective engine (V2)

This ADR locks both.

## Decision

### 1 · Event-sourced substrate

Twin state is DERIVED from an append-only event log. State is never stored mutably as source of truth. Rationale (per Phase 29 blueprint §1.2):

- Time-travel: any prior date reconstructable
- Correction transparency: nothing silently overwritten
- Perspective folding: same log reduces differently per viewer
- Cross-project pattern lending: patterns translate cleanly

### 2 · Event log table schema

```sql
CREATE TABLE hammerex_nex_twin_events (
  -- Identity
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  event_number    BIGSERIAL,        -- monotonic insertion order per partition

  -- Scope
  merchant_slug   TEXT NOT NULL,
  project_id      UUID NOT NULL,

  -- Event content
  kind            TEXT NOT NULL,    -- 'photo.uploaded' | 'delivery.received' | ...
  version         INTEGER NOT NULL DEFAULT 1,  -- event schema version
  payload         JSONB NOT NULL,

  -- Attribution
  actor_kind      TEXT NOT NULL CHECK (actor_kind IN ('user', 'agent', 'cron', 'system')),
  actor_id        TEXT,

  -- Causation + correlation
  correlation_id  UUID,             -- links related event chain
  causation_id    UUID,             -- the event that caused this one

  -- Temporal
  observed_at     TIMESTAMPTZ NOT NULL,  -- when the thing happened
  emitted_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),  -- when we recorded it

  -- Evidence
  evidence_ref    JSONB,            -- source citation
  confidence      TEXT CHECK (confidence IN ('low', 'medium', 'high')),

  -- Approval state (per ES-01 correction #10)
  approval_state  TEXT NOT NULL DEFAULT 'auto_appended'
                    CHECK (approval_state IN ('auto_appended', 'pending_approval', 'approved', 'rejected'))
) PARTITION BY RANGE (observed_at);
```

Partitioned by month. Indexes:
- `(project_id, kind, observed_at DESC)` for perspective queries
- `(project_id, observed_at DESC)` for timeline queries
- `(merchant_slug, observed_at DESC)` for merchant-wide feeds

### 3 · Event schema versioning

- Every event kind has a versioned Zod schema at `src/lib/nex/twin-live/events/<kind>.v<N>.ts`
- Additive schema changes: version stays
- Breaking schema changes: new version emitted alongside old for 90 days · consumers migrate · old version deprecated

### 4 · Approval state per event (per ES-01 correction #10)

- **auto_appended** — high-confidence event, immediately applied to state
- **pending_approval** — medium-confidence Vision AI event · merchant reviews before state applies
- **approved** — merchant confirmed
- **rejected** — merchant refused · event remains in log for audit but state reducer ignores

### 5 · V0 perspectives · exactly two

At V0, Twin state reduces into two perspectives:

- **Merchant perspective** — full detail · financial columns visible
- **Homeowner perspective** — customer-friendly · financial detail hidden · merchant-controlled visibility per event

**Deferred to V2:** per-Trade-Brain perspective engine, insurer perspective, admin/audit perspective.

Rationale: V0 needs two viewers to work. Brain perspectives are query composition on top of the same event log; adding them later is additive, not a migration.

### 6 · V0 BIM ingest · deferred

BIM ingest (IFC 4.3 · Forge · iTwin.js embed) requires enterprise-scale files that small merchants don't have. Twin V0 ships without BIM. Photos + drawings + measurements suffice.

**Deferred to V1:** IFC ingest · Forge Viewer embed · iTwin.js embed.

### 7 · Snapshot cache strategy

- Weekly snapshot per project generated by cron
- Cached in `hammerex_nex_twin_snapshots` (keyed by project + week-ending date)
- Serves timeline queries · rebuild from events on cache miss
- Snapshots are cache · never truth · deletable + regeneratable

### 8 · Retention

- Events append-only forever (no deletion outside GDPR RTBF)
- Partitions older than 24 months move to cold storage tier
- Cold storage remains queryable · slower
- GDPR RTBF cascade: soft-delete then hard-delete after 30-day appeal window · legal retention floor per jurisdiction observed with PII redaction

### 9 · What lives in the log · what does not

Log:
- Every project state change
- Every Vision AI finding
- Every merchant approval / rejection
- Every homeowner action
- Every delivery · milestone · variation · inspection

Not log:
- Snapshot cache (derived · regeneratable)
- Perspective projections (derived · regeneratable)
- BIM blobs (in Supabase Storage · URIs in log only)
- Photos + videos (Storage · URIs in log only)

## Consequences

**Positive:**
- Event log becomes the durable truth · every future Twin capability composes on top
- Time-travel + correction transparency + perspective folding all become free capabilities
- Cross-project pattern lending (Phase 29 blueprint §5.3) enabled by consistent event schema
- Merchant + homeowner perspective serves V0 · adding more perspectives is additive query work

**Negative:**
- Event log will grow to millions of events per year at merchant density · partitioning + archival strategy mandatory from day one
- Weekly snapshot cache required for perf · additional infrastructure
- BIM ingest deferred means enterprise merchants can't use Twin V0 for BIM workflows · commercial impact on enterprise pipeline for Y1
- Two perspectives at V0 means Brain-perspective queries wait until V2

**Neutral:**
- Additional perspectives added via query composition · no schema changes required
- Event schema versioning gives runway for evolution without breakage

## Alternatives Considered

- **Mutable state rows instead of event log** · rejected · loses time-travel, correction transparency, perspective folding · these ARE the Phase 29 value proposition
- **Kafka or dedicated event store instead of Postgres** · rejected · scale-inappropriate per ES-01 · Postgres partitioning + pg_cron sufficient to 100k merchants
- **Store BIM as inline JSON in event payload** · rejected · size + query cost prohibitive · Storage URI reference is correct pattern
- **Full 4-perspective V0 (Merchant + Homeowner + Insurer + Admin)** · rejected · V0 scope discipline · Insurer + Admin arrive at V2 when demand exists
- **TimescaleDB extension for time-series performance** · considered · deferred to V3+ · native partitioning + pg_cron adequate at V0 scale
- **Event log per merchant (partition by merchant)** · rejected · project scoping is the natural boundary · month-partitioning serves query patterns better

## Implementation Impact

- `hammerex_nex_twin_events` new table (partitioned)
- `hammerex_nex_twin_snapshots` new table (cache)
- `hammerex_nex_twin_perspectives` (optional cache · rebuilt from log)
- Event schema files at `src/lib/nex/twin-live/events/`
- Event contract registry per ES-03 §4
- State reducer at `src/lib/nex/twin-live/reducer/`
- Vision reconciler at `src/lib/nex/twin-live/reconciler.ts`
- Weekly snapshot cron via pg_cron
- Partition-management cron for month rollover

## Enforcement

- Event log NEVER mutable — enforced by Postgres `NO UPDATE` policy at row level
- Every event kind must have registered Zod schema · CI blocks PR without schema
- Emitter cannot bypass approval-state check · integration test verifies
- Weekly restore-from-events test in CI validates reducer correctness

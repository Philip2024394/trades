### 2.2 · R-17 versioning thresholds · founder decision required

**Draft proposal (from ADR-0314a.2.m):**

| Trigger | Threshold | Founder-override behaviour |
|---|---|---|
| Body content change | > 30% diff (algorithm below) | Founder can always force version regardless of threshold |
| Claim delta | Any attribute-tier change | Always fires · no threshold |
| Authority change | Any change to `source_reference` | Always fires |
| Status transition | DRAFT → UNDER_REVIEW → AUTHORITATIVE → DEPRECATED | Always fires |
| Domain reclassification | Any change to `domain` field | Always fires · Guardian-authored only |
| Founder-declared significance | Founder-authored flag | Always fires · overrides all thresholds |

**Diff algorithm alternatives:**

| Algorithm | Cost | Semantic vs surface | Notes |
|---|---|---|---|
| **Levenshtein / edit distance (draft default)** | Low | Surface | Simple · deterministic · fast |
| Word-level Jaccard | Low | Surface | Whitespace-tokenised · language-agnostic |
| Semantic-similarity (embedding cosine) | High | Semantic | Detects meaning-preserving edits · non-deterministic across model versions |
| Structural diff (JSON-aware) | Medium | Structural | Best for structured records like accommodation_business rows |

**Threshold percentage alternatives:**

| % | Behaviour | Consequences |
|---|---|---|
| 20% | Conservative | Many versions · large `nex.record_versions` growth · every minor edit versioned |
| **30% (draft default)** | Balanced | Meaningful edits versioned · trivial edits not |
| 50% | Permissive | Only substantial rewrites versioned · risk of losing intermediate history |
| 70% | Very permissive | Only near-total rewrites versioned · content history mostly lost |

**Founder decision points:**
- Diff algorithm choice
- Threshold percentage
- Which status transitions warrant automatic versioning (all vs promotion-only vs demotion-only vs none)
- Retention policy (all-time · N years · founder decides)
- Whether version rows carry their own `evidence` row per LAM Rule 5 · or derive from parent

**Recommendation (Master AI · labelled · non-binding):** Levenshtein / edit distance for algorithm (fastest · deterministic · matches R-17 automatic-versioning intent) · 30% threshold as starting point. Founder tunes after Stage 1 observes real change rates in Stage 4 loop.

**Master AI does NOT lock these values. Founder authors final.**

## Item 4 · Options 1–4 for R-10 impact reconciliation · Master AI recommendation

Per Stage 1 Companion ADR Batch Part D · four options presented for founder review. The exact treatment is authored in Stage 2 ADR-0314a.2.i · NOT locked in this pre-flight. This item PRESENTS the options + Master AI recommendation.

### Option 1 · Retroactive sentinel · bulk operation

Apply `authorised_by = "founder_legacy_pre_R10_v1"` (or similar sentinel) to all 175 rows in a single Stage 2 operation. Preserves AUTHORITATIVE status. Sentinel value is founder-authored per ADR-0314a.2.i.

**Pros:**
- Fastest reconciliation
- Preserves AUTHORITATIVE status of legitimate content
- Simple audit trail (one sentinel · one operation)

**Cons:**
- Bulk-treats subject-matter and operational tier the same way
- May be inappropriate for operational-scope rows (Business Operating System · AI Rules · Platform Architecture) which are meta-doctrine · not subject-matter
- Founder cannot easily differentiate between "legitimate pre-R10 content" and "row that would fail R-10 gate if applied today"

### Option 2 · Demote all 175 to `truth_engine_ok`

Remove AUTHORITATIVE status from all 175 rows · leave at `truth_engine_ok` state pending re-verification. Rows remain queryable but not flagged as AUTHORITATIVE.

**Pros:**
- Cleanest R-10 gate enforcement (no legacy exemptions)
- Every AUTHORITATIVE row post-Stage-2 has explicit founder authorisation

**Cons:**
- Immediately loses AUTHORITATIVE status for 175 legitimate rows
- Chat/NEX1 may show these as less-authoritative during Stage 3-4 verification
- Regression risk (Test J may fail if any Chat query previously depended on the AUTHORITATIVE flag)
- Cannot be undone silently (each row that regains AUTHORITATIVE needs Stage 2 R-10 gate approval)

### Option 3 · Per-row founder review

175 individual founder decisions. Each row reviewed · founder authors `authorised_by` explicitly or demotes.

**Pros:**
- Highest audit quality per row
- Founder catches any legacy content that should NOT be AUTHORITATIVE

**Cons:**
- Impractical at 175 rows (equivalent to reviewing 175 mini-ADRs)
- Blocks Stage 2 completion by weeks
- Diminishing marginal value beyond the first ~30 rows

### Option 4 · Hybrid · subject-matter tier bulk-sentinel · operational tier individual review

- Subject-matter tier (~85% · ~150 rows) receives sentinel `authorised_by = "founder_legacy_pre_R10_v1"` per Option 1
- Operational-scope tier (~15% · ~25 rows) reviewed individually per Option 3
- Sentinel value is founder-authored per ADR-0314a.2.i
- Reversibility: any row can later be individually amended if founder decides subject-matter tier row warrants explicit review

**Pros:**
- Balances speed and audit quality
- Handles the ~85% legitimate trades content quickly
- Preserves per-row founder scrutiny for the operational-scope tier (where meta-doctrine warrants care)
- Consistent with §7.10 M1 anti-inflation discipline (subject-matter tier is Trade Knowledge candidate meta-Domain · currently deferred · sentinel preserves state without pre-committing to that Domain decision)

**Cons:**
- Requires per-row classification into subject-matter vs operational-scope (Master AI proposes a split · founder approves)
- Sentinel-tagged rows are less audited than individually-reviewed rows
- Founder may later regret bulk-sentinel if a subject-matter row turns out to have been inappropriate

### Master AI recommendation (labelled · non-binding · founder amends)

**Recommend Option 4 · hybrid**, but WITH the founder's amendment:

> *"Trade Knowledge itself is still deferred as a possible future meta-Domain. So no automatic reconciliation based only on the current classification."*

Refined Option 4 · per founder's steer:

- Subject-matter tier bulk-sentinel is **conditional** · does NOT pre-commit to Trade Knowledge being a Domain
- Sentinel value is authored per Stage 2 ADR-0314a.2.i · NOT this pre-flight
- If Trade Knowledge is later promoted to a Domain (via §7.10 M1 deferral resolution), the sentinel-tagged rows can be reclassified as Trade-Knowledge-Domain AUTHORITATIVE
- If Trade Knowledge is NOT promoted, the sentinel-tagged rows remain in Supabase legacy substrate with sentinel authorised_by · treated as physical representation per §7.8 J1 Rule 15
- Operational-scope tier (~25 rows) reviewed individually · per-row founder authorisation via ADR-0314a.2.i

**Alternative recommendation if founder prefers Option 3 for all 175:** Master AI can produce a per-row review document (175 mini-decisions · Founder authors each). This defers Stage 2 completion but produces highest audit quality.

**Master AI does NOT lock any option. Founder decides at Stage 2 ADR-0314a.2.i authoring.**

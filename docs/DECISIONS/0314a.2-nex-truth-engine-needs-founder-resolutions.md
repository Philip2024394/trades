## Question 1 · R-10 · Autonomous verifier promotion · ✅ ANSWERED

### 1 · Question

The verifier can currently promote records to `AUTHORITATIVE` status without founder authorisation. Evidence: 93 of 115 AUTHORITATIVE records in the 1,000-row Supabase sample have `authorised_by=null`. Is this autonomous verifier promotion INTENTIONAL and should it become canonical doctrine?

### 2 · Current observed evidence

- 1,000-row cross-tab (Path C · ADR-0314a):
  - AUTHORITATIVE × `authorised_by=null`: **93 rows**
  - AUTHORITATIVE × `authorised_by=Philip`: **22 rows**
  - Ratio ≈ 4.2 : 1 in favour of unauthored authoritative
- Status transitions from `knowledge_feedback.context` (all 402 feedback rows):
  - UNDER_REVIEW → AUTHORITATIVE: 61 (founder approvals)
  - DRAFT → DEPRECATED: 178 (founder rejections of drafts)
  - **Zero observed founder-approval events targeting the 93 authored-by-null records.** They reached AUTHORITATIVE without a `knowledge_feedback` row.

### 3 · Founder decision · **CANDIDATE C** · recorded 2026-09-11

> *"Truth Engine should be capable of autonomously determining a truth_engine_ok verdict, but promotion to AUTHORITATIVE must be governed by the authorisation policy of the specific LAM logical object type. This preserves NEX autonomy while preventing a single promotion rule from granting inappropriate authority to every knowledge type. Founder-controlled knowledge such as People-Say may require explicit founder authorisation, while other object types may be eligible for autonomous promotion when their defined provenance, confidence, validation, and governance requirements are satisfied. The existing 93 authorised_by=null AUTHORITATIVE records are historical observations and must not be automatically grandfathered into the new doctrine. They require impact analysis and selective re-verification according to the authorisation policy established for their respective logical object types."*
>
> — Philip · 2026-09-11

**Doctrinal distinction locked by this decision:**

> `truth_engine_ok ≠ AUTHORITATIVE`
>
> **Authority = Truth Engine verdict + LAM object-type authorisation policy → promotion decision**

### 4 · Canonical rule · R-10.v1.0.0

**Verifier verdicts terminate at `truth_engine_ok` unless the target LAM object type's authorisation policy explicitly permits autonomous promotion to `AUTHORITATIVE`.**

Each LAM object type must carry an authorisation policy declaring:

- Whether autonomous promotion to `AUTHORITATIVE` is permitted (yes / no)
- If **yes** · the required confidence floor · provenance chain · validation gates · governance conditions the object must satisfy simultaneously
- If **no** · the required founder authorisation path (e.g. explicit `knowledge_feedback` row with `feedback_kind='approval'` and `feedback_source ∈ founder_authorised_set`)

Object-type authorisation policies are declared in dedicated companion ADRs (see follow-ups). Each policy is founder-approved individually. Silent assumption of a policy is forbidden (D-10 explicitly scoped).

### 5 · Scope

### 6 · What happens when unknown · fail-closed (D-4)

If the authorisation policy for a given LAM object type has not yet been declared in a companion ADR, the verifier defaults to `truth_engine_ok` and does NOT promote to AUTHORITATIVE.

- Object stays at `truth_engine_ok`
- Router surfaces `truth_status='truth_engine_ok'` in every response
- No authoritative-by-default under any circumstance
- No fabrication of an implicit policy

### 7 · What happens when violated · G-2 non-bypass

- Certification failure for the rule
- Audit event emitted with `bypass_attempt` marker
- Substrate write path rejects the transition
- Verifier cannot proceed until either (a) its rule set is amended by ADR OR (b) the object-type policy is updated to permit autonomous promotion

## Question 2 · R-18 · Verifier identity meaning · ✅ ANSWERED

### 1 · Question

Two verifier identities have been observed: `quality-checker@677` (7 detections 2026-08-06) and `quality-checker@22408` (1 detection 2026-08-08). What does the `@<number>` suffix mean? Are these separate deployments · separate versions · separate rule subsets · or worker instance IDs?

### 2 · Current observed evidence

- `quality-checker@677` produced 7 of 8 contradictions on 2026-08-06 across multiple record categories (staircase · door · balustrade · voice/tone)
- `quality-checker@22408` produced 1 contradiction on 2026-08-08 (baluster workers connection)
- Two days between activities
- Numerical range of the suffixes (~677 vs ~22408) suggests either PID-like ephemeral IDs or version increments
- No documentation observable

### 3 · Founder decision · **CANDIDATE A** · recorded 2026-09-11

> *"The observed verifier identities quality-checker@677 and quality-checker@22408 should be treated as worker or process instance identities, not as rule-set versions or deployment identities. A verifier instance must not implicitly define or alter Truth Engine doctrine. Rule-set identity and version must be explicit, independently versioned, and substrate-neutral. Multiple verifier instances may execute the same certified Truth Engine rule set, but each invocation must record the verifier instance identity separately from the rule-set version so that results remain deterministic, reproducible, auditable, and attributable. If future deployments intentionally use a different rule set, that difference must be explicitly versioned and certified rather than inferred from an instance identifier."*
>
> — Philip · 2026-09-11

**Doctrinal principle locked by this decision:**

> **The verifier instance ID must never be used as the rule-set version.**
>
> Verifier instance identity and rule-set identity are two independent audit dimensions. Both must be recorded per verdict. Neither substitutes for the other.

### 4 · Canonical rule · R-18.v1.0.0

Verifier instance IDs (e.g. `quality-checker@677` · `quality-checker@22408`) are **worker / process instance identifiers only**. They do NOT:

- Define a rule set
- Alter Truth Engine doctrine
- Establish a rule-set version
- Confer autonomy or authority

Multiple verifier instances may execute the same certified Truth Engine rule set concurrently. Each verdict record MUST carry two independent fields:

- **`verifier_instance_id`** · the worker/process identifier (e.g. `quality-checker@677`)
- **`rule_set_version`** · independently versioned (e.g. `TE_ruleset.v1.0.0`)

These two fields are separate columns · never conflated · never one derived from the other.

If a future deployment intentionally uses a different Truth Engine rule set, that difference MUST be explicitly declared in an ADR that:

- Names the new rule-set version
- Certifies its rule set against the certification principle (deterministic · reproducible · versioned · substrate-neutral · fail-closed)
- Documents the scope

Instance identifier changes alone (new PID · worker restart · scale-out replica) MUST NOT be interpreted as rule-set changes.

### 5 · Scope

All physical Truth Engine verifiers · current (`quality-checker@677` · `quality-checker@22408`) and future (any `nex_dev` verifier · any additional Supabase verifier · any cross-substrate verifier).

Applies to every verdict record in every audit substrate:

- Supabase `audit_log` (20,224 rows)
- Supabase `contradictions.detected_by`
- Future `nex_dev` truth-engine audit table (naming TBD per ADR-0314b)

Substrate-neutral (D-3): the separation of instance identity and rule-set version is uniform across substrates.

### 6 · What happens when unknown · fail-closed (D-4)

If a verifier attempts to write a verdict without BOTH `verifier_instance_id` AND `rule_set_version` present:

- Guardian rejects the write
- No verdict is stored
- No promotion occurs
- The event is logged as `insufficient_verdict_provenance`

Under no circumstance may a verdict be rendered anonymous or unversioned.

### 7 · What happens when violated · G-2 non-bypass

If a verifier issues verdicts using the instance ID as the rule-set version (e.g. writing `@677` in place of a `rule_set_version` field), or omits either field:

- Certification failure
- All verdicts issued in this mode are audit-flagged as `identity_version_conflation`
- Verifier cannot proceed until rule-parity re-certification with the two fields properly separated
- Founder notified via governance-required audit path

### 8 · Affects existing data? · NO CHANGES · historical evidence preserved

The two observed verifier instances (`quality-checker@677` · 7 detections · `quality-checker@22408` · 1 detection) remain historical evidence. Per founder directive 2026-09-11:

> *"do not investigate or reinterpret the two historical instances by changing existing records yet"*

Master AI does NOT:

- Modify the 8 contradiction rows they produced
- Change their `detected_by` values
- Backfill missing `rule_set_version` fields on their historical verdicts
- Reinterpret their historical output

Existing rows remain as observed. This decision establishes doctrine going forward. Historical reconciliation (if ever needed) is a separate future ADR that would run AFTER a canonical rule-set version has been declared and certified.

### 9 · Migration / re-verification eventually required · FORWARD-ONLY · SELECTIVE

- **Immediate:** No re-verification of historical rows. No modification of `contradictions` · `audit_log` · `knowledge_records` produced by `@677` or `@22408`.

## Question 3 · R-11 · `confidence_band` vs `confidence_score` authoritative · ✅ ANSWERED

### 1 · Question

`confidence_scores` rows carry both a `confidence_band` (categorical: high/medium/low) and a `confidence_score` (numeric 0-100). Sample rows show `confidence_band='high'` and `confidence_score=0` in the same row. Which field is authoritative?

### 2 · Current observed evidence

- Sample from `confidence_scores`: 3 rows with `record_id='business_nex_business_brain_v1'` all have `confidence_band='high'` and `confidence_score=0`
- `source_type='NEX_authored'` on all three
- Router (ADR-0311 Rule B4) already normalises to numeric 0-1 at read time · but the input scale must be settled to know which raw value to normalise

### 3 · Founder decision · **CANDIDATE B** · recorded 2026-09-11

> *"The Truth Engine requires one precise, machine-readable confidence authority. The observed numeric confidence_score provides the deterministic precision required for reproducible verification and Router normalisation, while confidence_band is a categorical representation suitable for human-readable display and retrieval presentation. Making both fields authoritative would create two competing confidence authorities and would make divergence resolution ambiguous. Therefore confidence_score is authoritative, confidence_band is derived from it according to explicitly versioned thresholds, and any existing or future divergence between the stored band and the authoritative score is treated as a data-quality inconsistency rather than as competing truth. The Router normalises the authoritative 0–100 score to the canonical 0–1 confidence value."*
>
> — Philip · 2026-09-11

**Doctrinal principle locked by this decision:**

> **`confidence_score` (numeric 0-100) is the single authoritative confidence field. `confidence_band` is derived / display-only.**
>
> Divergence between a stored `band` and the authoritative `score` is a **data-quality inconsistency**, never competing truth.

### 4 · Canonical rule · R-11.v1.0.0

**Confidence authority:**

- `confidence_score` (numeric 0-100) is the **authoritative** confidence field for every LAM object type that carries confidence.
- `confidence_band` (categorical: high · medium · low · etc.) is **derived · display-only**.
- Truth Engine reads `confidence_score`. Guardian reads `confidence_score`. Router reads `confidence_score`.

**Router normalisation contract (aligns ADR-0311 Rule B4):**

```
KnowledgeResponse.confidence      = confidence_score / 100         // canonical 0-1
KnowledgeResponse.confidence_raw  = { value: <confidence_score>, scale: "0-100" }
```

The Router MUST NOT read `confidence_band` as an input to its normalised confidence value. If `confidence_band` is surfaced to callers (e.g. for UI convenience), it MUST be flagged as `derived: true` in the response.

**Band derivation (future companion ADR):**

`confidence_band` may be re-derived from `confidence_score` using an explicitly versioned threshold table (e.g. `band_derivation.v1.0.0`: 0-33 → low · 34-66 → medium · 67-100 → high). The threshold table is founder-authored in a future ADR (candidate slot: **ADR-0314a.2.j · Confidence Band Derivation Thresholds**). Until that ADR lands, the Router does not derive bands · it surfaces the stored `confidence_band` value verbatim under `derived: true` with a `band_derivation_pending` flag.

**Divergence treatment:**

When a stored `confidence_band` disagrees with the band that would be derived from `confidence_score` (e.g. stored `band='high'` alongside `score=0` · which would derive to `low`), that row is a **data-quality inconsistency**. It is NOT a contradiction (LAM object type 8). It is NOT a promotion blocker at the confidence layer. Guardian may flag it for later reconciliation but does not reject the write. Truth Engine's decisions remain grounded in `confidence_score` alone.

### 5 · Scope

Confidence (LAM object type 9). Every canonical row that carries a confidence field, on every substrate:

- Supabase `confidence_scores` (4,228 rows)

## Question 6 · R-17 · Significant-change definition for versioning · ✅ ANSWERED

### 1 · Question

`record_versions` has only 22 rows for 3,627 records (0.6% version coverage). Not every edit produces a version. What constitutes a "significant change" that triggers versioning?

### 2 · Current observed evidence

- Sample versions carry `version='1.0.0'` · '1.1.0' semver-style

### 3 · Founder decision · **CANDIDATE C** · recorded 2026-09-11

> *"Versioning must preserve meaningful historical state without generating unnecessary version noise from every persisted edit. Founder-declared significance alone would make reproducibility and consistent enforcement dependent on manual intervention, while automatic versioning of every edit would produce excessive versions and obscure meaningful changes. NEX will therefore use deterministic threshold-based rules to identify significant changes and automatically create a version when a defined threshold or version-trigger condition is met. Founder Authority retains the ability to explicitly force a version where the change is materially significant even if an automatic threshold is not met. The exact significance categories, thresholds, status-transition triggers and override semantics must be separately founder-authored, versioned and auditable; this decision establishes the versioning architecture and does not itself define those thresholds."*
>
> — Philip · 2026-09-11

**Doctrinal principle locked by this decision:**

> **NEX uses threshold-based automatic versioning for objectively significant changes, with explicit Founder Authority override capability.**
>
> The **architecture** for determining significance is locked in this ADR. The **actual thresholds** are separately founder-authored, versioned, and auditable (deferred to ADR-0314a.2.m).

**Founder guardrail locked verbatim (recorded 2026-09-11):**

> **"A change must never be considered insignificant merely because it falls below an automatic threshold when Founder Authority explicitly declares it significant. And conversely, the automatic system must not silently invent its own significance thresholds."**

This bidirectional discipline is doctrinal:

1. Founder Authority always outranks the automatic threshold (upward override).
2. The automatic system MUST NOT invent thresholds. Every threshold used at runtime MUST trace to a founder-authorised ADR (downward discipline).

### 4 · Canonical rule · R-17.v1.0.0

**Versioning architecture:**

- Versions are created by ONE of two paths:
  - **Automatic path (deterministic thresholds)** · a version is created when a defined significance trigger is met (e.g. `status → AUTHORITATIVE` transition · body diff exceeds a founder-authored threshold · schema migration event · etc). Thresholds live in ADR-0314a.2.m.
  - **Founder-override path** · a version is created when Founder Authority explicitly declares the change significant, regardless of whether the automatic threshold was met.
- No third path exists. Versions are NEVER created by ad-hoc invented thresholds. Versions are NEVER omitted when Founder Authority declares a change significant.

**Determinism (D-1):**

- Every significance threshold used at runtime MUST reference a founder-authorised threshold ID + version (e.g. `versioning_thresholds.v1.0.0`)
- Same object state + same threshold version + same trigger event → same outcome (version created OR not)
- No LLM-adjacent significance detection without explicit founder-per-change approval

**Versioning idiom (unchanged from Supabase practice):**

- Versions use semver-style identifiers (e.g. `1.0.0` · `1.1.0`)
- Every version snapshot preserves body_markdown at the time of the version
- Version rows are immutable (LAM Rule 10)
- Every version records `versioning_threshold_version` (which threshold set governed the creation) alongside `version_id` for reproducibility (D-6)

**Founder override recording:**

- When Founder Authority forces a version below automatic threshold: version row carries `override=true` · `overridden_by=<founder identity>` · `override_reason` field
- When Founder Authority forces a version even where automatic system would have skipped: same fields · same audit trail
- Overrides are auditable (D-7) · reproducible (G-3)

**What ADR-0314a.2.m must deliver (deferred):**

The actual significance categories · thresholds · status-transition triggers · override semantics are NOT locked by R-17. They will be defined in a separate founder-authored ADR: **ADR-0314a.2.m · Versioning Thresholds and Significance Triggers**. Illustrative candidates previously listed in R-17's candidate section (e.g. `>20% body diff` · `status upgrade to AUTHORITATIVE` · `schema migration`) are **illustrative only · not adopted by this ADR**.

### 5 · Scope

All version-carrying structures on any substrate:

- Supabase `record_versions` (22 rows observed)

### 6 · What happens when unknown · fail-closed (D-4)

- **Thresholds not yet authored (before ADR-0314a.2.m lands):** automatic versioning is **DISABLED**. Guardian rejects any auto-versioning attempt. Founder Authority can still explicitly create versions via the override path · those versions are recorded with `override=true` and cite `versioning_threshold_version=pending` in the audit trail
- **A trigger fires but the threshold criterion is ambiguous:** Guardian rejects the auto-version. Version not created. Event logged as `threshold_ambiguous`. Founder can still explicitly create the version
- **Founder Authority declares a change significant but no threshold row matches the trigger event:** version IS created via override path. The absence of a matching threshold does not block the founder-declared version

### 3 · Founder decision · **CANDIDATE A+ (two-tier model)** · recorded 2026-09-11

The pure Candidate A ("must share graph_edges") was rejected as too rigid: legitimate connections can exist before a graph edge has been created, and absence of an edge does not prove implausibility. ## Question 12 · R-20 · Cross-record contradiction detection · ✅ ANSWERED · FINAL RESOLUTION

### 1 · Question

All 8 observed contradictions are internal (record_a_id === record_b_id). Does the verifier attempt cross-record contradiction detection at all? This blocks ADR-0314c (Cross-Substrate Contradiction Detection).

### 2 · Current observed evidence

- All 8 contradictions internal to one record
- No cross-record contradiction observed
- Cannot determine from output whether the verifier tries and finds none, or does not attempt

### 3 · Founder decision · **CANDIDATE B** · recorded 2026-09-11

> *"The absence of observed cross-record contradictions in the current corpus does not establish that contradiction detection is or should be limited to individual records. NEX must distinguish between the observed behaviour of the existing verifier and the intended logical capability of the Truth Engine. Cross-record contradiction detection is necessary to support a complete contradiction surface and provides the foundation for the later cross-substrate contradiction requirement already established by TE7. However, cross-record detection must not be allowed to manufacture contradictions from semantic similarity, keyword overlap, different wording, missing information or differences in scope. A contradiction requires a deterministic governed rule establishing logical incompatibility between the relevant claims. Reference fixtures must therefore prove both positive detection and important non-contradiction cases before the verifier is certified."*
>
> — Philip · 2026-09-11

**Doctrinal principles locked by this decision:**

> **The Truth Engine contradiction verifier is permitted and intended to attempt cross-record contradiction detection.**
>
> **Contradiction detection is not restricted to a single record.** The Truth Engine contradiction surface must support:
> 1. Internal contradiction detection within one logical object/record
> 2. Cross-record contradiction detection between distinct logical objects where governed claims address the same logical subject, claim key, entity, fact or mutually exclusive proposition
>
> **Observed absence of cross-record contradictions is NOT evidence that cross-record detection is unnecessary.**

**Critical distinctions locked:**

> - A cross-record contradiction requires a **deterministic governed rule establishing that two claims are logically incompatible**
> - Mere **difference**, **disagreement**, **missing information**, **different wording**, or **different scope** does NOT constitute contradiction
> - Cross-record contradiction detection must NEVER infer contradiction solely from **semantic similarity**, **keyword overlap**, or an **LLM judgment**
> - Where the verifier cannot deterministically establish incompatibility, the result must remain **unknown** / **candidate finding** rather than authoritative contradiction

### 4 · Canonical rule · R-20.v1.0.0

**Cross-record contradiction detection architecture:**

The Truth Engine contradiction surface (LAM object type 8 · TE6 · TE7) covers both:

1. **Internal contradictions** (`record_a_id === record_b_id`) — as observed today · continue existing behaviour
2. **Cross-record contradictions** (`record_a_id ≠ record_b_id`) — same-substrate first · cross-substrate deferred to ADR-0314c

**A cross-record contradiction is issued only when:**

- A deterministic governed rule (per ADR-0314a.2.r · deferred) establishes that two claims are logically incompatible
- Both records resolve to valid canonical objects (per R-13 vocabulary · per LAM object types)
- The claim keys, entities, subjects, or facts under comparison are equivalent under the governed comparison rule
- The governed rule declares the specific incompatibility class (e.g. mutually-exclusive-fact · numerically-incompatible-per-domain-threshold · policy-conflict · etc.)

**Cross-record detection MUST NOT:**

- Infer contradiction from semantic similarity alone
- Infer contradiction from keyword overlap alone
- Infer contradiction from LLM judgment alone
- Treat difference in wording as contradiction
- Treat different scope as contradiction (records may address the same topic at different scopes without contradicting)
- Treat missing information as contradiction (per R-07's Unknown ≠ False distinction · restated)

**Reference fixture requirements (locked · fixture set deferred to ADR-0314a.1):**

Reference fixtures MUST include, at minimum:

1. **Known positive cross-record contradiction** — two records making logically incompatible claims about the same subject · verifier MUST detect
2. **Known negative pair** — two records that are merely different but not contradictory · verifier MUST NOT mark as contradiction
3. **Same-subject different-scope pair** — two records addressing the same subject at different scopes · verifier MUST NOT mark as contradiction
4. **Unresolved / insufficient-evidence pair** — two records where incompatibility cannot be deterministically established · verifier MUST return `unknown` · never `contradiction`
5. **Internal contradiction regression case** — a same-record contradiction (per current verifier behaviour) · verifier MUST continue to detect

Fixture set is delivered by ADR-0314a.1 · not this ADR.

**Cross-record verdict shape (extends ADR-0311 output envelope):**

Every cross-record contradiction row must preserve, for BOTH participating objects:

- `record_a_id` + `record_a_substrate` + `record_a_snapshot_ref`
- `record_b_id` + `record_b_substrate` + `record_b_snapshot_ref`
- LAM identity of both objects
- Provenance chain for both objects (per LAM Rule 5)
- Evidence citations that justified the incompatibility finding
- Confidence value for the finding (per R-11 · numeric 0-1)
- Version of both records at the time of the finding (per R-17)
- Authority context for both objects (per R-10's object-type authorisation policy)
- `contradiction_rule_id` + `contradiction_rule_version` (per ADR-0314a.2.r · deferred)
- `contradiction_class` (mutually-exclusive-fact · numerically-incompatible · policy-conflict · etc.)

**Cross-substrate contradiction detection remains deferred:**

R-20 establishes the **logical contradiction surface** including cross-record. It does NOT:

- Author or implement cross-substrate contradiction detection (deferred to **ADR-0314c** · reserved)
- Extend the surface to Router-side comparison of same-subject records across `nex_dev` and Supabase (deferred to ADR-0314c)
- Create the runtime infrastructure that finds cross-substrate contradiction candidates

Cross-substrate detection is a separate capability building on top of R-20. ADR-0314c authors the cross-substrate detector · this ADR authors the logical surface it will operate over.
